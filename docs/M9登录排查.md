# M9 后处理反复弹登录：给接收方 AI 的排查说明

> **云端 M9 二瞬相关内容仅供学习参考。**

目标：修复接收者手机上相册 M9 后处理反复提示登录的问题。先取证再改，不能直接把“未登录”判断改成已登录。本文是排查与修改方向，不代表已确认接收者的根因。

## 1. 已知基线与参考机的真实修复

- 历史排查基线为 r3 的相册编辑 v6，也适用于使用同一编辑器的 r2 和 r4。r11 使用相册编辑 v15，先核对其当前哈希和代码路径。
- 目标机型 xuanyuan，小米 15 Ultra；发布包固定 ROM 为 OS4.0.4.0.XOACNXM。
- 登录相关应用是 **相册编辑器 com.miui.mediaeditor**，不是相机 com.android.camera，也不是相册主程序 com.miui.gallery。
- r3 内相册编辑器文件：`apps/MediaEditor-v6.apk`，versionName 为 2.10.40.4.8。
- 该 APK SHA256：`42ebc2c4827e19f087e7c5d079d2c30592059746b8129f0b28a44b10d3d7c808`。
- r3 仅更新相机至 v13，编辑器沿用已包含账号修复的 v6。不要误以为本次相机 v13 修复了登录。

参考机的证据：系统已登录小米账号，但编辑器进程中 `AccountManager.getAccountsByType("com.xiaomi")` 返回 0 个。原 `addAccount` 没有返回可启动的 Intent，用户点登录后只会得到取消/失败，反复弹窗。补丁在此分支打开系统账号选择授权界面，由用户选择自己的账号；随后编辑器可见账号数从 0 变为 1，日志 `MME_CloudLegendM9Processor` 出现 `uploadFile: result = Success`，用户最终确认增强、保存、重开正常。

这支持“应用账号可见性”问题，但不能据此断言接收者一定同因，更不能直接认定系统签名是唯一根因。Android 的系统账号登录状态和某个应用能否看到该账号是两个层面；授权状态不会跟着 APK 分发。

## 2. 先核对现场，不要马上重编 APK

1. 读用户设备机型、ROM、Android 用户/分身状态，确认相册、编辑器和小米账号位于同一用户。系统分身、应用双开、工作资料可能有独立账号环境，不能默认都是 user 0。
2. 确认实际安装的是上述编辑器 APK。应用商店更新或开机保管脚本可能使版本与预期不同；**以设备当前 APK 哈希为准，不能只看版本号**。
3. 如果不是基线版本，先备份当前 APK，再告知用户，使用发布包里的编辑器覆盖测试；不要为登录问题重装整套模块或重启手机。
4. 如哈希一致，复现“打开 M9→开始增强→登录→再次增强”，记录完整一轮。账号选择由用户操作；上传照片需用户自己决定。

Windows PowerShell 只读示例（先用 `adb devices` 选择接收者自己的序列号；不要照搬作者序列号）：

```powershell
adb devices
$deviceSerial = '填接收者设备序列号'
adb -s $deviceSerial shell getprop ro.product.device
adb -s $deviceSerial shell getprop ro.build.version.incremental
adb -s $deviceSerial shell am get-current-user
$editorApkPath = (adb -s $deviceSerial shell pm path com.miui.mediaeditor |
    Select-Object -First 1).Trim() -replace '^package:', ''
adb -s $deviceSerial shell sha256sum $editorApkPath
```

如有多个用户/分身，以上默认包路径查询不足以证明当前界面所属用户，需要结合 Activity/进程所属用户检查。不要在不确定时跨用户改账号。

日志示例（保存在接收者电脑本地，复现后 Ctrl+C 结束，不用清空 logcat）：

```powershell
adb -s $deviceSerial logcat -v threadtime -T 1 |
    Select-String 'HybridGalleryAccount|AccountUtil|CloudLegendM9|LegendaryActivity|login cancel|SecurityException|AndroidRuntime' |
    Tee-Object -FilePath .\m9-login-local.txt
```

仅用日志关键词定位；过滤日志可能漏掉系统账号服务错误，必要时另抓一次短时完整日志。分享日志前去除账号名、账号 ID、token、cookie、授权链接和云端结果 URL。诊断新增日志仅记账号数量、回调分支、错误类型/错误码，不输出凭据。

**注意：在 adb shell、root shell 或另外写的测试 APK 里查询到账号，不代表编辑器能看到账号。需要在编辑器自己的进程和 Context 中验证。** `dumpsys account` 也不能替代这个验证，更不要把完整账号转储发给别人。

## 3. 按日志分支处理

### A. 没有 HybridGalleryAccount 日志

先确认 APK 哈希与实际启动包/进程；确认已经操作到账号检查与登录回调。日志没出现本身不能直接说明补丁没装，可能尚未经过该分支、机型判断没命中或被日志过滤漏掉。

检查 `Build.DEVICE` 是否真为 xuanyuan（某些机型伪装模块会改变它）。现有修复按该值限制；若未命中，应先确认伪装来源与真实机型，不能简单全机型放开。

### B. HybridGalleryAccountCount 一直是 0

这是账号可见性或查询异常方向，优先处理此层，暂时不要改云 token 逻辑。

- 看有没有 `login returned no visible account; opening system chooser`。
- 有：系统账号选择页有没有真的出现，用户是否选了现有的小米账号？返回后数量是否仍为 0？同时检查 `account UI returned OK but no account is visible`。
- 没有：看原 `addAccount` 是否返回了非空 Intent、抛异常，或用户取消。**现有补丁仅覆盖“原回调没有 Intent，且没有可见账号”这一分支，并没有覆盖所有 OEM 返回路径。**
- 如果原 Intent 存在，但启动后取消/空结果，仍没有真实账号：可在用户主动点登录的同一流程中，增加一次系统账号选择兜底。要有单次状态标记，防止取消后自动无限重开；用户取消就正常退出。
- 如果 `getResult()` 抛 `OperationCanceledException`、`AuthenticatorException`、I/O 异常或查询抛 `SecurityException`，分别记录脱敏错误，不把它们全部当成“已登录”。只有证据支持时，才对合适失败分支提供一次用户可见的系统选择入口。
- 系统选择返回 OK 后，再查真实可见账号。若设备存在授权传播延迟，可安排少量有界的异步重查（例如 200/500/1000ms，总计不超过 2 秒），不能在主线程 sleep，不能无限轮询；仍为 0 就提示授权未完成。
- 检查接收者是否取消/限制了编辑器的账号相关授权，以及账号服务是否被禁用；不要要求先退出整个小米账号或清账号服务数据。

### C. 数量变为 1，但依旧提示登录

不要继续反复打开账号选择页。向下追踪实际失败点：

- 原账号检查得到的真实账号是否进入 M9 processor；是否另一个进程或另一个 Android 用户仍读不到。
- 是否已有真实账号，但获取 service token/认证信息失败；记录请求的服务类型和脱敏错误码，不记录 token 内容。
- 是否本地预检查已通过，但服务器返回 401/403、账号授权拒绝、服务区域/资格或网络错误。只有看到实际响应才能作此判断。
- 验证系统时间/网络和官方账号服务能否正常授权。若服务端拒绝重签客户端或该账号资格，修改本地登录布尔值不能解决，需如实报告限制。
- 只有确认现有 token 过期且原官方授权接口支持刷新时，才走原刷新/重新授权流程；不要从别的应用、手机或备份中提取并移植 token。

“上传成功”只证明到了上传环节，最终验收还需要处理完成、保存、退出重开正常。

## 4. 本基线 APK 的代码定位

以下是 **2.10.40.4.8 编辑器基线**的混淆类名，换版本必须按调用/字符串重新定位，不能照搬路径或资源 ID。

- `smali_classes2/ga0/e.smali`
  - `a(Context): String`：调用 `AccountManager.getAccountsByType("com.xiaomi")`，为空则返回空；补丁日志为 `HybridGalleryAccountCount`。
  - `c(...)`：原登录发起路径，调用账号服务 `addAccount`，认证类型使用原来的 `passportapi`；先核对方法声明，不猜参数。
- `smali_classes2/ga0/a.smali`
  - `run(AccountManagerFuture)`：原 addAccount 回调，读取 Bundle 的 `intent`。
  - 现有补丁：仅 xuanyuan、Intent 为空且 `ga0/e.a(Context)` 为空时，调用公共 `AccountManager.newChooseAccountIntent`，账号类型只限 `com.xiaomi`。
  - 沿用原来的 `ActivityResultRegistry` 注册和 Activity 生命周期清理；不另起不受控 Activity。
- `smali_classes2/ga0/d.smali`
  - 结果回调 `n(Object)`：即使 RESULT_OK，也重新查询真实账号；没有可见账号时保留失败/取消，不伪报登录成功。
- `yn/j`：M9 云处理的本地账号预检查入口之一；搜索 `uploadFile failed, not login`、`CloudLegendM9Processor` 与 `ga0/e.a` 的调用链。

核心方向的伪代码（不是可以直接编译的 smali）：

```text
用户主动点击登录
  → 原 addAccount 流程
  → 若已有真实可见账号：沿用原成功逻辑
  → 若原流程未完成授权，且本轮尚未兜底：
       打开系统账号选择页，仅列出 com.xiaomi
       用户选择后重新查询编辑器可见账号
       真正可见才进入原成功回调
  → 取消、失败、超时：结束本轮，允许用户手动再试
```

系统选择接口参考：

```java
AccountManager.newChooseAccountIntent(
    null, null, new String[]{"com.xiaomi"},
    null, null, null, null
);
```

不要误以为只加 GET_ACCOUNTS 或改 Manifest 就能自动获得其他应用/用户的账号可见性。

## 5. 修改边界与验收

- 优先只改编辑器 APK，保留已正常的滤镜、调色保存、徕卡入口和云渲染代码。不改相机/驱动/KSU 模块/框架/账号数据库，不重启；先备份原 APK 并准备回退。
- 不能改 `ga0/e.a` 返回伪造账号、“demo”、固定 ID，不能把未登录检查改恒真，也不能屏蔽所有服务端错误。
- 不修改 AccountManager/system_server，不全局开放账号权限，不关闭 SELinux，不改签名检查策略，不卸载清数据强装。沿用设备已经配置且可用的 APK 安装方式；遇到签名问题先停下确认。
- 不复制作者或其他人的账号、应用数据、token、cookie；账号选择由接收者本人完成。
- 重编后检查 DEX 引用/重复类、签名及原生库 16KB 对齐。保留原资源和 native 字节，避免为账号小改引入渲染回归。安装前告知用户，只替换编辑器；force-stop 后重开即可。
- 验收：原循环复现得到解释 → 用户主动授权 → 编辑器真实账号数大于 0 → 无反复登录 → 用户自愿上传测试图 → 云处理完成 → 保存重开效果正常。再检查普通编辑和调色保存未回归。
- 向接收者报告：原因证据、具体改动类/分支、输出 APK 哈希、安装结果、是否真实处理成功、回退文件；没有完成云处理不要写“全修好”。

无需为这件事重装整包。r3 安装器成功后会自动重启一次；单独编辑器登录调试应使用独立 APK 测试流程，不能误触发整包自动重启。
